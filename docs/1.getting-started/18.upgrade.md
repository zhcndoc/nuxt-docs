## 升级 Nuxt

### 最新版本

要将 Nuxt 升级到[最新版本](https://github.com/nuxt/nuxt/releases)，请使用 `nuxt upgrade` 命令。

::code-group{sync="pm"}

```bash [npm]
npx nuxt upgrade
```

```bash [yarn]
yarn nuxt upgrade
```

```bash [pnpm]
pnpm nuxt upgrade
```

```bash [bun]
bun x nuxt upgrade
```

```bash [deno]
deno x nuxt upgrade
```

::

### 夜版发布渠道

要使用 Nuxt 的最新构建版本并测试新功能（尚未正式发布），请阅读[夜版发布渠道](/docs/4.x/guide/going-further/nightly-release-channel)指南。

## 测试 Nuxt 5

Nuxt 5 **目前正在开发中**。在发布之前，可以测试许多 Nuxt 5 从 Nuxt 版本 4.2+ 的重大更改。

### 选择使用 Nuxt 5

首先，将 Nuxt 升级到 [最新版本](https://github.com/nuxt/nuxt/releases)。

然后，您可以将 `future.compatibilityVersion` 设置为匹配 Nuxt 5 的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  future: {
    compatibilityVersion: 5,
  },
})
```

当您将 `future.compatibilityVersion` 设置为 `5` 时，您在 Nuxt 配置中的默认值将更改为选择 Nuxt v5 的行为，包括：

- **Vite Environment API**：自动启用新的 [Vite 环境 API](/docs/4.x/getting-started/upgrade#migration-to-vite-environment-api)，以改进构建配置
- **区分大小写的路由**：页面路由[严格匹配 URL 的大小写](/docs/4.x/getting-started/upgrade#case-sensitive-routing)，与 Nitro 保持一致
- **标准化页面名称**：页面组件名称将[匹配其路由名称](/docs/4.x/getting-started/upgrade#normalized-page-component-names)，以确保 `<KeepAlive>` 行为一致
- **`clearNuxtState` 重置为默认值**：`clearNuxtState` 将[把状态重置为其初始值](/docs/4.x/getting-started/upgrade#respect-defaults-when-clearing-usestate)，而不是将其设置为 `undefined`
- **非异步 `callHook`**：[`callHook` 可能返回 `void`](/docs/4.x/getting-started/upgrade#non-async-callhook)，而不是始终返回 `Promise`
- **注释节点占位符**：仅客户端组件使用[注释节点而不是 `<div>`](/docs/4.x/getting-started/upgrade#client-only-comment-placeholders)作为 SSR 占位符，修复 scoped styles hydration 问题
- **更严格的副作用导入**：生成的 `tsconfig.json` 启用 [`noUncheckedSideEffectImports`](/docs/4.x/getting-started/upgrade#stricter-side-effect-imports)，以匹配 TypeScript 7 的默认设置
- **Vue Options API 已禁用**：为了减小客户端包体积，[Options API 会从客户端包中编译移除](/docs/4.x/getting-started/upgrade#vue-options-api-disabled-by-default)
- **类型化页面**：默认启用 [`experimental.typedPages`](/docs/4.x/getting-started/upgrade#typed-pages-enabled-by-default)，用于类型检查路由
- **忽略 TypeScript `baseUrl`**：生成的 TypeScript 配置[不再使用 `compilerOptions.baseUrl`](/docs/4.x/getting-started/upgrade#typescript-baseurl-is-ignored)解析 Nuxt 别名
- Nuxt 5 的其他改进和变更会陆续提供

::note
本节内容在最终发布之前可能会有所更改，因此如果您正在使用 `future.compatibilityVersion: 5` 测试 Nuxt 5，请定期回来查看。
::

重大或显著的变化将在下面注明，并附上向后/向前兼容的迁移步骤。

### 区分大小写的路由

🚦 **影响级别**：最低

#### 变更内容

使用 `compatibilityVersion: 5` 时，页面路由将以区分大小写的方式匹配 URL，与 Nitro 保持一致。例如，`/About` 不再匹配 `pages/about.vue`。

#### 迁移步骤

更新链接，使其使用与页面路由相同的大小写。若要保持不区分大小写的匹配：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  router: {
    options: {
      sensitive: false,
    },
  },
})
```

### `jiti` 不再打包

🚦 **影响级别**：中等

#### 变更内容

Nuxt 不再依赖 [`jiti`](https://github.com/unjs/jiti)。在 bundler 外部加载的文件（`nuxt.config.ts`、`modules/` 中的文件以及 layer 配置）现在由运行时本身导入。

**你仍然可以使用 TypeScript 编写配置。** Nuxt 5 要求 Node `22.19` 或更高版本，此时类型剥离默认开启，因此 `nuxt.config.ts` 和 TypeScript 模块会原生加载。运行时有两件过去由 `jiti` 代为处理、但现在不会处理的事情：猜测文件扩展名，以及编译会生成代码的 TypeScript 语法。

否则，这两类问题只有在 Nuxt 加载文件时才会暴露出来，因此生成的 `node` tsconfig 现在会按照运行时所见的方式描述环境（将 `module` 和 `moduleResolution` 设置为 `nodenext`，并加入 [`erasableSyntaxOnly`](https://www.typescriptlang.org/tsconfig/#erasableSyntaxOnly)），TypeScript 也会提前报告这两类问题。

这只涵盖 `nuxt.config`、`modules/` 和 layer 配置。你的应用代码和 `shared/` 代码会经过 Vite，并按照一直以来的方式解析。如果你需要之前的行为，可以覆盖配置：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    nodeTsConfig: {
      compilerOptions: {
        module: 'preserve',
        moduleResolution: 'bundler',
        erasableSyntaxOnly: false,
      },
    },
  },
})
```

#### 变更原因

每次安装 Nuxt 时，都会引入 `jiti` 来加载少量文件，而其中大多数文件现在运行时已经可以在没有辅助的情况下加载。移除它可以减小默认安装的体积。

#### 迁移步骤

**1. 为相对导入添加文件扩展名。**

`nuxt.config.ts`、`modules/` 和 layer 配置中的相对导入需要显式指定扩展名：

```diff [nuxt.config.ts]
- import { myPlugin } from './build/my-plugin'
+ import { myPlugin } from './build/my-plugin.ts'
```

TypeScript 会以 `TS2835` 报告缺少扩展名。请注意，它的快速修复建议使用 `./build/my-plugin.js`；应填写文件实际使用的扩展名（`.ts`），Node 会直接解析该扩展名。

裸包导入（`import { defu } from 'defu'`）不受影响。

**2. 使用可擦除的 TypeScript 语法。**

类型注解会被擦除，但会生成运行时代码的语法则无法使用。在配置文件和模块文件中，将以下内容替换为：

- 用 `const` 对象替换 `enum Foo {}`
- 用普通导出替换 `namespace`／`module` 代码块
- 将构造函数参数属性（`constructor(private x: string) {}`）替换为显式赋值
- 实验性装饰器

TypeScript 会以 `TS1294` 为你报告这些问题。

**3. 如果你发布 layer 或模块，请提供编译后的 JavaScript。**

这一点仅适用于包。无论配置如何，运行时都拒绝从 `node_modules` 内的任何文件中剥离类型，因此使用 TypeScript 编写的已发布入口无法原生加载，不论 Node 版本有多新。发布前请先编译为 JavaScript；如果你的包包含 `nuxt.config`，请将其输出为 `nuxt.config.mjs`。否则，每个使用该包的项目都必须安装 `jiti`。

这不适用于你自己项目中的 layer：`layers/*/nuxt.config.ts` 会原生加载。

**4. 如果仍然需要 `jiti`，请安装它。**

`jiti` 现在是可选的 peer dependency。安装后，只要运行时无法自行加载文件，Nuxt 就会自动将其作为回退方案使用：

::code-group{sync="pm"}

```bash [npm]
npm i -D jiti
```

```bash [yarn]
yarn add -D jiti
```

```bash [pnpm]
pnpm add -D jiti
```

```bash [bun]
bun add -D jiti
```

::

无论使用哪个 Node 版本，`nuxt.schema` 文件始终需要 `jiti`：其中的 JSDoc 注解是通过导入时转换读取的，而不是通过导入文件读取的。

随之而来的还有一项较小的变更：`postcss.plugins` 中指定的 PostCSS 插件现在由运行时解析，因此仅能通过 Nuxt `alias` 条目解析的插件名称将不再加载。请使用包名称或路径。

### 迁移到 Vite 环境 API

🚦 **影响级别**：中等

#### 变化内容

Nuxt 5 迁移到 Vite 6 的新 [环境 API](https://vite.dev/guide/api-environment)。该 API 正式化了环境的概念，并提供了对每个环境配置的更好控制。

之前，Nuxt 使用单独的客户端和服务器 Vite 配置。现在，Nuxt 使用共享的 Vite 配置，并配备特定于环境的插件。这些插件使用 `applyToEnvironment()` 方法来针对特定环境。

::note
Vite 环境 API 在 Nuxt 5 中始终启用。`experimental.viteEnvironmentApi` 选项已被移除。
::

**关键变化：**

1. **不再支持特定于环境的 `extendViteConfig()`**：`extendViteConfig()` 中的 `server` 和 `client` 选项已被弃用，使用时将显示警告。

2. **更改插件注册**：使用 `addVitePlugin()` 注册的 Vite 插件，如果仅针对一个环境（通过传递 `server: false` 或 `client: false`）将不会调用其 `config` 或 `configResolved` 钩子。

3. **共享配置**：`vite:extendConfig` 和 `vite:configResolved` 钩子现在与共享配置一起工作，而不是单独的客户端／服务器配置。

#### 变更原因

Vite 环境 API 提供了：
- 更好的一致性：确保开发与生产构建之间差异最小化
- 更细粒度的环境特定配置控制
- 改进的性能与插件架构
- 支持自定义环境，而不仅仅是客户端和服务器

#### 迁移步骤

##### 1. 迁移到使用 Vite 插件

我们建议您使用 Vite 插件，而不是 `extendViteConfig`、`vite:configResolved` 和 `vite:extendConfig`。

```ts
// 之前
extendViteConfig((config) => {
  config.optimizeDeps.include.push('my-package')
}, { server: false })

nuxt.hook('vite:extendConfig' /* or vite:configResolved */, (config, { isClient }) => {
  if (isClient) {
    config.optimizeDeps.include.push('my-package')
  }
})

// 之后
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // 这里可以设置全局 vite 配置
  },
  configResolved (config) {
    // 这里可以访问完整解析后的 vite 配置
  },
  configEnvironment (name, config) {
    // 这里可以设置特定环境的 vite 配置
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

##### 2. 迁移 Vite 插件以使用环境

您可以使用插件中的新 `applyToEnvironment` 钩子，而不是使用 `addVitePlugin` 结合 `server: false` 或 `client: false`。

```ts
// 之前
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    config.optimizeDeps.include.push('my-package')
  },
}), { client: false })

// 之后
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // 这里可以设置全局 vite 配置
  },
  configResolved (config) {
    // 这里可以访问完整解析后的 vite 配置
  },
  configEnvironment (name, config) {
    // 这里可以设置特定环境的 vite 配置
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

::read-more{to="https://vite.dev/guide/api-environment" target="_blank"}
了解更多关于 Vite 环境 API 的内容
::毛片免费观看

默认情况下，如果你未手动设置，Vue 会赋予组件名等同于组件文件名的名称。

```bash [目录结构]
├─ components/
├─── SomeFolder/
├───── MyComponent.vue
```

此时，Vue 认为组件名为 `MyComponent`。如果你想和 `<KeepAlive>` 搭配使用，或在 Vue DevTools 中识别该组件，需要使用这个名称。

但 Nuxt 的自动导入会使用 `SomeFolderMyComponent` 作为名称。

此次变更后，这两个名称将保持一致，Vue 生成的组件名将匹配 Nuxt 的命名模式。

#### 迁移步骤

确保你在使用 `@vue/test-utils` 的 `findComponent` 进行测试，以及任何依赖组件名的 `<KeepAlive>` 中使用更新后的名称。

或者，你现在可以通过以下配置禁用此行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizeComponentNames: false,
  },
})
```

### Unhead v2

🚦 **影响级别**：最小

#### 变化内容

用于生成 `<head>` 标签的 [Unhead](https://unhead.unjs.io/) 升级到版本 2。尽管大多数兼容，但底层 API 有若干破坏性变更：

- 移除属性：`vmid`、`hid`、`children`、`body`
- 不再支持 Promise 类型的输入
- 默认使用 Capo.js 对标签进行排序

#### 迁移步骤

上述变更对应用影响较小。

如果遇到问题，请检查：

- 你是否使用了已移除的属性

```diff
useHead({
  meta: [{ 
    name: 'description', 
    // meta 标签无需 vmid 或 key    
-   vmid: 'description' 
-   hid: 'description'
  }]
})
```

- 如果你使用了 [模板参数](https://unhead.unjs.io/docs/head/guides/plugins/template-params) 或 [别名标签排序](https://unhead.unjs.io/docs/head/guides/plugins/alias-sorting)，需要显式启用相关插件。

```ts
import { AliasSortingPlugin, TemplateParamsPlugin } from '@unhead/vue/plugins'

export default defineNuxtPlugin({
  setup () {
    const unhead = injectHead()
    unhead.use(TemplateParamsPlugin)
    unhead.use(AliasSortingPlugin)
  },
})
```

虽然非必须，建议将所有从 `@unhead/vue` 的导入改为 `#imports` 或 `nuxt/app`。

```diff
-import { useHead } from '@unhead/vue'
+import { useHead } from '#imports'
```

如果仍有问题，可通过启用 `head.legacy` 配置回退到 v1 行为：

```ts
export default defineNuxtConfig({
  unhead: {
    legacy: true,
  },
})
```

### SPA Loading 屏幕的新 DOM 位置

🚦 **影响级别**：最小

#### 变化内容

客户端渲染页面（`ssr: false`）时，加载屏幕（默认值为 `~/app/spa-loading-template.html`；在 Nuxt 4 中改为 `~/spa-loading-template.html`）渲染在 Nuxt 应用根节点内：

```html
<div id="__nuxt">
  <!-- spa loading template -->
</div>
```

现在，加载屏幕默认渲染在 Nuxt 应用根节点旁边：

```html
<div id="__nuxt"></div>
<!-- spa loading template -->
```

#### 变更原因

这样能确保加载屏幕在 Vue 应用的 Suspense 解析完前一直存在，避免出现闪白。

#### 迁移步骤

如果你曾用 CSS 或 `document.querySelector` 定位加载屏幕元素，请更新选择器。你可以利用新的 `app.spaLoaderTag` 和 `app.spaLoaderAttrs` 配置来辅助定位。

或者，你可以通过以下配置恢复到旧行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    spaLoadingTemplateLocation: 'within',
  },
})
```

### 解析后的 `error.data`

🚦 **影响级别**：最小

之前抛出的错误对象中若有 `data` 属性，未自动解析。现在已自动解析，并可通过错误对象访问。虽然这是一项修复，但如果你依赖旧行为并手动解析，这将属于破坏性变更。

#### 迁移步骤

更新自定义 `error.vue`，删除对 `error.data` 的额外解析：

```diff
  <script setup lang="ts">
  import type { NuxtError } from '#app'

  const props = defineProps({
    error: Object as () => NuxtError
  })

- const data = JSON.parse(error.data)
+ const data = error.data
  </script>
```

### 更细粒度的内联样式

🚦 **影响级别**：中等

#### 变化内容

Nuxt 现在仅对 Vue 组件的样式进行内联，而不再内联全局 CSS。

之前，Nuxt 会内联包括全局样式在内的所有 CSS，并移除针对单独 CSS 文件的 `<link>`。现在仅对 Vue 组件相关的 CSS 内联（此前这些样式会产生独立的 CSS Chunk）。这能更好地平衡以下目标：减少网络请求数量（首屏加载时不会为每个页面或组件单独请求 `.css` 文件）、提升全局 CSS 缓存效率，以及减少初始请求体积。

#### 迁移步骤

此特性可通过配置完全控制。你可以通过设置 `inlineStyles: true` 恢复之前的行为，即对全局 CSS 也进行内联：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  features: {
    inlineStyles: true,
  },
})
```

### 解析后扫描页面元数据

🚦 **影响级别**：最小

#### 变化内容

我们现在在调用 `pages:extend` 钩子之后扫描页面元数据（在 `definePageMeta` 中定义），而不是在调用之前。

#### 变更原因

这样做是为了允许扫描用户希望在 `pages:extend` 中添加的页面的元数据。我们仍然提供了一个机会，即在新的 `pages:resolved` 钩子中更改或覆盖页面元数据。

#### 迁移步骤

如果你想覆盖页面元数据，请在 `pages:resolved` 中进行，而不是在 `pages:extend` 中。

```diff
  export default defineNuxtConfig({
    hooks: {
-     'pages:extend'(pages) {
+     'pages:resolved'(pages) {
        const myPage = pages.find(page => page.path === '/')
        myPage.meta ||= {}
        myPage.meta.layout = 'overridden-layout'
      }
    }
  })
```

或者，你可以通过以下方式恢复之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    scanPageMeta: true,
  },
})
```

### 共享预渲染数据

🚦 **影响级别**：中等

#### 变化内容

我们启用了一个此前的实验功能，用于在不同页面之间共享 `useAsyncData` 和 `useFetch` 调用的数据。详见[原始 PR](https://github.com/nuxt/nuxt/pull/24894)。

#### 变更原因

该功能会自动在预渲染页面之间共享负载中的 _数据_。当预渲染使用 `useAsyncData` 或 `useFetch`，并且在不同页面请求相同数据的站点时，能显著提升性能。

例如，如果你的网站在每个页面都需要调用 `useFetch`（比如用于获取菜单导航数据，或 CMS 中的站点设定），这些数据会在首次预渲染使用它的页面时只被请求一次，并缓存起来供其他页面的预渲染使用。

#### 迁移步骤

确保你数据的唯一键总是能解析到相同的数据。例如，如果你使用 `useAsyncData` 请求与特定页面相关的数据，应提供一个唯一匹配该数据的键。（`useFetch` 会自动为你处理）

```ts [app/pages/test/[slug\\].vue]
// 在动态页面（例如 `[slug].vue`）中，这样使用是不安全的，因为路由的 slug 会影响请求的数据，
// 而 Nuxt 无法感知这一点，因为它未反映在 key 中。
const route = useRoute()
const { data } = await useAsyncData(async () => {
  return await $fetch(`/api/my-page/${route.params.slug}`)
})
// 正确做法是使用唯一标识请求数据的 key。
const { data } = await useAsyncData(route.params.slug, async () => {
  return await $fetch(`/api/my-page/${route.params.slug}`)
})
```

或者，你可以禁用此功能：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    sharedPrerenderData: false,
  },
})
```

### `useAsyncData` 和 `useFetch` 中默认的 `data` 和 `error` 值

🚦 **影响级别**：最小

#### 变化内容

从 `useAsyncData` 返回的 `data` 和 `error` 对象默认现在为 `undefined`。

#### 变更原因

之前 `data` 初始化为 `null`，但在 `clearNuxtData` 中被重置为 `undefined`。`error` 初始化为 `null`。此更改旨在提升一致性。

#### 迁移步骤

如果你之前检查过 `data.value` 或 `error.value` 是否为 `null`，可以改为检查其是否为 `undefined`。

::tip
你可以通过运行 `npx codemod@latest nuxt/4/default-data-error-value` 自动完成此步骤
::

### 移除调用 `useAsyncData` 和 `useFetch` 的 `refresh` 时 `dedupe` 选项的布尔值支持

🚦 **影响级别**：最小

#### 变化内容

之前调用 `refresh` 时可以传递 `dedupe: boolean`。它们分别是 `cancel`（`true`）和 `defer`（`false`）的别名。

```ts twoslash [app/app.vue]
// @errors: 2322
const { refresh } = await useAsyncData(() => Promise.resolve({ message: 'Hello, Nuxt!' }))

async function refreshData () {
  await refresh({ dedupe: true })
}
```

#### 变更原因

为使语义更清晰，我们移除了这些布尔别名。

该问题产生于为 `useAsyncData` 添加 `dedupe` 选项时，布尔值最终变成了相反的含义。

`refresh({ dedupe: false })` 表示 **不取消现有请求以优先执行该请求**。但在 `useAsyncData` 选项中传递 `dedupe: true` 表示 **若已有挂起请求则不发起新请求**。（详见[PR](https://github.com/nuxt/nuxt/pull/24564#pullrequestreview-1764584361)）

#### 迁移步骤

迁移很简单：

```diff
  const { refresh } = await useAsyncData(async () => ({ message: 'Hello, Nuxt 3!' }))
  
  async function refreshData () {
-   await refresh({ dedupe: true })
+   await refresh({ dedupe: 'cancel' })

-   await refresh({ dedupe: false })
+   await refresh({ dedupe: 'defer' })
  }
```

::tip
你可以通过运行 `npx codemod@latest nuxt/4/deprecated-dedupe-value` 自动完成此步骤
:::

### 在 `useAsyncData` 和 `useFetch` 中清空 `data` 时尊重默认值

🚦 **影响级别**：最小

#### 变化内容

如果你为 `useAsyncData` 提供了自定义的 `default` 值，那么在调用 `clear` 或 `clearNuxtData` 时，将会使用该默认值重置，而不仅仅是简单地置为空。

#### 变更原因

用户通常会设置合适的空值（如空数组），以避免在遍历时检查 `null` 或 `undefined`。清空数据时应尊重这一设定。

### 清空 `useState` 时尊重默认值

🚦 **影响级别**：最小

#### 变化内容

当设置 `compatibilityVersion: 5` 时，`clearNuxtState` 会将状态重置为由 `useState` 的 `init` 函数提供的初始值，而不是将其设置为 `undefined`。这使得 `clearNuxtState` 的行为与已重置默认值的 `clearNuxtData` 保持一致。

#### 变更原因

当 `clearNuxtState` 将状态设为 `undefined` 时，依赖该状态的组合式函数可能会崩溃，因为它们期望状态始终具有有效形态（例如，不能对 `undefined` 访问属性）。重置为 `init` 提供的值可确保状态始终有可用的默认值。

#### 迁移步骤

如果你依赖 `clearNuxtState` 把状态设置为 `undefined`，可以显式传递 `{ reset: false }`：

```diff
- clearNuxtState('myKey')
+ clearNuxtState('myKey', { reset: false })
```

或者，你可以通过以下配置恢复之前行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    defaults: {
      useState: {
        resetOnClear: false,
      },
    },
  },
})
```

你也可以在不设置 `compatibilityVersion: 5` 的情况下，当前选择启用此行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    defaults: {
      useState: {
        resetOnClear: true,
      },
    },
  },
})
```

### `useAsyncData` 和 `useFetch` 中 `pending` 值的对齐

🚦 **影响级别**：中等

`useAsyncData`、`useFetch`、`useLazyAsyncData` 和 `useLazyFetch` 返回的 `pending` 现在是计算属性，仅当 `status` 也处于挂起状态时才为 `true`。

#### 变化内容

当传入 `immediate: false` 时，`pending` 会在首次请求发起之前保持为 `false`，这与之前的行为不同（之前首次请求前 `pending` 总是为 `true`）。

#### 变更原因

此变更使 `pending` 的含义与 `status` 属性一致：当请求进行时，两者均为挂起状态。

#### 迁移步骤

如果你依赖 `pending` 属性，请确保逻辑考虑到新行为：`pending` 仅在 `status` 也处于挂起时为 `true`。

```diff
  <template>
-   <div v-if="!pending">
+   <div v-if="status === 'success'">
      <p>Data: {{ data }}</p>
    </div>
    <div v-else>
      <p>Loading...</p>
    </div>
  </template>
  <script setup lang="ts">
  const { data, pending, execute, status } = await useAsyncData(() => fetch('/api/data'), {
    immediate: false
  })
  onMounted(() => execute())
  </script>
```

你也可以暂时使用下列配置恢复旧行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    pendingWhenIdle: true,
  },
})
```

### `useAsyncData` 和 `useFetch` 中 key 变更行为

🚦 **影响级别**：中等

#### 变化内容

在 `useAsyncData` 或 `useFetch` 中使用响应式 key 时，当 key 变化会自动重新请求数据。设置 `immediate: false` 时，`useAsyncData` 只有在数据已请求过一次后，key 变化才会重新请求。

之前，`useFetch` 的行为略有不同：在 key 变化时它会始终请求数据。

现在，`useFetch` 与 `useAsyncData` 行为一致——只有在数据已请求过一次后，key 变化才会重新请求。

#### 变更原因

确保 `useAsyncData` 与 `useFetch` 行为一致，避免意外请求。

若设置了 `immediate: false`，需要调用 `refresh` 或 `execute`，否则数据永远不会被请求。

#### 迁移步骤

此更改通常会提升预期行为，但如果你希望在非立即加载的 `useFetch` 中通过改变 key 或选项自动请求，现在需要手动首次触发。

```diff
  const id = ref('123')
  const { data, execute } = await useFetch('/api/test', {
    query: { id },
    immediate: false
  )
+ watch(id, () => execute(), { once: true })
```

若希望禁用此行为：

```ts
// 或在 Nuxt 配置中全局禁用
export default defineNuxtConfig({
  experimental: {
    alwaysRunFetchOnKeyChange: true,
  },
})
```

### `useAsyncData` 和 `useFetch` 中数据浅层响应性

🚦 **影响级别**：最小

从 `useAsyncData`、`useFetch`、`useLazyAsyncData` 和 `useLazyFetch` 返回的 `data` 对象现在是 `shallowRef`，而非普通的 `ref`。

#### 变化内容

新数据到达时，依赖 `data` 的内容仍然是响应的，因为整个对象会被替换。但如果代码修改了数据对象内部的属性，则不会触发响应性更新。

#### 变更原因

这对于深层嵌套的对象和数组带来**显著**的性能提升，因为 Vue 无需监控每个属性或数组项。且通常 `data` 应该是不可变的。

#### 迁移步骤

大多数情况下无需变化，但如果你依赖数据对象内部的响应性，有两种方案：

1. 在具体的组合式函数调用中开启深层响应性：

   ```diff
   - const { data } = useFetch('/api/test')
   + const { data } = useFetch('/api/test', { deep: true })
   ```

2. 在项目中全局更改默认行为（不推荐）：

   ```ts twoslash [nuxt.config.ts]
   export default defineNuxtConfig({
     experimental: {
       defaults: {
         useAsyncData: {
           deep: true,
         },
       },
     },
   })
   ```

::tip
你可以通过运行 `npx codemod@latest nuxt/4/shallow-function-reactivity` 自动完成此步骤
::

### `builder:watch` 中使用绝对路径监听

🚦 **影响级别**：最小

#### 变化内容

Nuxt 的 `builder:watch` 钩子现在发出的路径是绝对路径，而不是相对于项目 `srcDir` 的相对路径。

#### 变更原因

此变更支持监听 `srcDir` 之外的路径，并且更好地支持图层等复杂模式。

#### 迁移步骤

我们已经主动迁移了已知使用该钩子的官方 Nuxt 模块，详见 [issue #25339](https://github.com/nuxt/nuxt/issues/25339)。

如果你是模块作者，并想同时兼容 Nuxt v3 和 Nuxt v4，可以使用下面代码来适配路径：

```diff
+ import { relative, resolve } from 'node:fs'
  // ...
  nuxt.hook('builder:watch', async (event, path) => {
+   path = relative(nuxt.options.srcDir, resolve(nuxt.options.srcDir, path))
    // ...
  })
```

::tip
你可以通过运行 `npx codemod@latest nuxt/4/absolute-watch-path` 自动完成此步骤
::

### 移除 `window.__NUXT__` 对象

#### 变化内容

在应用完成 hydration 后，我们移除了全局的 `window.__NUXT__` 对象。

#### 变更原因

这为多应用模式（[#21635](https://github.com/nuxt/nuxt/issues/21635)）铺平道路，并让我们专注于访问 Nuxt 应用数据的唯一途径 —— `useNuxtApp()`。

#### 迁移步骤

这些数据仍然可用，但需要通过 `useNuxtApp().payload` 访问：

```diff
- console.log(window.__NUXT__)
+ console.log(useNuxtApp().payload)
```

### 目录索引扫描

🚦 **影响级别**：中等

#### 变化内容

`app/middleware/` 文件夹内的子文件夹也会被扫描它们的 `index` 文件，这些文件也会被注册为项目中间件。

#### 变更原因

Nuxt 会自动扫描多个文件夹，包括 `app/middleware/` 和 `app/plugins/`。

`app/plugins/` 的子文件夹会扫描其 `index` 文件，我们希望在扫描目录时行为保持一致。

#### 迁移步骤

通常无需迁移，但如果你想恢复之前的行为，可以添加钩子过滤掉这些中间件：

```ts
export default defineNuxtConfig({
  hooks: {
    'app:resolve' (app) {
      app.middleware = app.middleware.filter(mw => !/\/index\.[^/]+$/.test(mw.path))
    },
  },
})
```

### 模板编译更改

🚦 **影响级别**：最小

#### 变化内容

之前 Nuxt 使用 `lodash/template` 编译位于文件系统中的模板，且采用 `.ejs` 文件格式/语法。

此外，我们还提供了一些模板工具函数（如 `serialize`、`importName`、`importSources`），用于这些模板中的代码生成，但现在不再提供。

#### 变更原因

在 Nuxt v3 中，我们使用了更灵活高效的“虚拟”语法和 `getContents()` 函数。

另外，`lodash/template` 曾出现多次安全问题。尽管对 Nuxt 项目影响不大（用于构建时，非运行时，且使用可信代码），但仍可能在安全审计中被提及。`lodash` 本身依赖较重，大多数项目并未使用它。

最后，在 Nuxt 内置代码序列化函数并不理想。更推荐使用像 [unjs/knitwork](https://github.com/unjs/knitwork) 这样的项目：它们可以作为你的项目依赖，在其中可以直接上报和修复安全问题，而不需要更新 Nuxt。

#### 迁移步骤

我们已经针对使用 EJS 语法的模块提交了 PR，但如果你需要自行处理，有三种兼容方案：

- 将字符串插值逻辑直接写入 `getContents()`。
- 使用自定义函数处理替换，如 https://github.com/nuxt-modules/color-mode/pull/240。
- 将 `es-toolkit/compat`（lodash template 的替代品）作为你项目的依赖，而非 Nuxt：

```diff
+ import { readFileSync } from 'node:fs'
+ import { template } from 'es-toolkit/compat'
  // ...
  addTemplate({
    fileName: 'appinsights-vue.js'
    options: { /* 一些选项 */ }
-   src: resolver.resolve('./runtime/plugin.ejs'),
+   getContents({ options }) {
+     const contents = readFileSync(resolver.resolve('./runtime/plugin.ejs'), 'utf-8')
+     return template(contents)({ options })
+   },
  })
```

最后，如果你使用了模板工具函数（如 `serialize`、`importName`、`importSources`），可以用 `knitwork` 替代：

```ts
import { genDynamicImport, genImport, genSafeVariableName } from 'knitwork'

const serialize = (data: any) => JSON.stringify(data, null, 2).replace(/"\{(.+)\}"(?=,?$)/gm, r => JSON.parse(r).replace(/^\{(.*)\}$/, '$1'))

const importSources = (sources: string | string[], { lazy = false } = {}) => {
  return toArray(sources).map((src) => {
    if (lazy) {
      return `const ${genSafeVariableName(src)} = ${genDynamicImport(src, { comment: `webpackChunkName: ${JSON.stringify(src)}` })}`
    }
    return genImport(src, genSafeVariableName(src))
  }).join('\n')
}

const importName = genSafeVariableName
```

::tip
你可以通过运行 `npx codemod@latest nuxt/4/template-compilation-changes` 自动完成此步骤
::。

这是之前 [3.12 配置更新](https://github.com/nuxt/nuxt/pull/27485) 的后续。改进默认配置主要遵循 [TotalTypeScript 的建议](https://www.totaltypescript.com/tsconfig-cheat-sheet)。

### TypeScript 配置拆分

🚦 **影响级别**：最小

#### 变化内容

Nuxt 现在为不同环境生成独立的 TypeScript 配置文件，以提升类型检测体验：

1. **新的 TypeScript 配置文件**：
   - `.nuxt/tsconfig.app.json` - 用于应用代码（Vue 组件、组合式函数等）
   - `.nuxt/tsconfig.server.json` - 用于服务端代码（Nitro/server 目录）
   - `.nuxt/tsconfig.node.json` - 用于构建时代码（模块、`nuxt.config.ts` 等）
   - `.nuxt/tsconfig.shared.json` - 用于共享代码（如类型和非环境依赖工具）
   - `.nuxt/tsconfig.json` - 旧版配置，保持向后兼容

2. **向后兼容性**：扩展 `.nuxt/tsconfig.json` 的项目仍将继续正常使用。

3. **项目引用选项（Project References）**：新项目或需要更好类型检查的可以采用。

4. **针对不同环境的上下文类型检查**：每个环境都拥有适合的编译选项和包含/排除规则。

5. **新增 `typescript.nodeTsConfig` 选项**：可定制 Node.js 构建时的 TypeScript 配置。

#### 变更原因

此变更带来多重好处：

1. **更好类型安全**：各环境具有匹配的全局变量和 API 检查。
2. **提升 IDE 体验**：针对不同代码部分提供更好的智能提示和错误报告。
3. **清晰分离**：避免服务端代码误引用客户端 API，反之亦然。
4. **性能提升**：TypeScript 能更高效地检查限定范围的代码。

例如：你的 `nuxt.config.ts` 中不再支持自动导入，之前 TS 不会报错。IDE 虽识别服务端目录的 `tsconfig.json`，但类型检查并未反映。此变化补足了这一差异。

#### 迁移步骤

**无需迁移**，现有项目保持不变即可继续工作。

若想利用更好的类型检查，可采用新的项目引用方式：

1. 更新根目录 `tsconfig.json`，添加项目引用：

   ::note
   如果你的 `tsconfig.json` 当前有一行 `"extends": "./.nuxt/tsconfig.json"`，**在添加引用之前请删除它**。项目引用与扩展是互斥的。
   ::

   ```json
   {
     // 如果存在则移除 "extends": "./.nuxt/tsconfig.json"
     "files": [],
     "references": [
       { "path": "./.nuxt/tsconfig.app.json" },
       { "path": "./.nuxt/tsconfig.server.json" },
       { "path": "./.nuxt/tsconfig.shared.json" },
       { "path": "./.nuxt/tsconfig.node.json" }
     ]
   }
   ```

2. 移除任何手写的服务端 `tsconfig.json`（例如 `server/tsconfig.json`）中对 `.nuxt/tsconfig.server.json` 的继承。

3. 更新类型检查脚本以使用项目引用构建：

   ```diff
   - "typecheck": "nuxt prepare && vue-tsc --noEmit"
   + "typecheck": "nuxt prepare && vue-tsc -b --noEmit"
   ```

4. 将所有类型增强代码归入相应上下文：
   - 应用端的增强放入 `app/` 目录。
   - 服务端的增强放入 `server/` 目录。
   - 应用与服务端共享的增强放入 `shared/` 目录。

    ::warning
    增强代码如果放在 `app/`、`server/` 或 `shared/` 目录之外，将无法兼容新的项目引用机制。
    ::

5. 如需定制 TypeScript 配置，在配置中添加：

   <!-- @case-police-ignore tsConfig -->

   ```ts
   export default defineNuxtConfig({
     typescript: {
       // 自定义 tsconfig.app.json
       tsConfig: {
         // ...
       },
       // 自定义 tsconfig.shared.json
       sharedTsConfig: {
         // ...
       },
       // 自定义 tsconfig.node.json
       nodeTsConfig: {
         // ...
       },
     },
     nitro: {
       typescript: {
         // 自定义 tsconfig.server.json
         tsConfig: {
           // ...
         },
       },
     },
   })
   ```

6. 更新 CI/构建脚本，确保使用新的项目引用方式。

新配置为可选项：提供更好的类型安全与智能提示，同时对现有项目保持完整兼容。

### 移除实验性功能配置

🚦 **影响级别**：最小

#### 变化内容

Nuxt 4 不再允许配置以下四个实验性功能：

- `experimental.treeshakeClientOnly`：将默认开启（自 v3.0 起即默认）
- `experimental.configSchema`：将默认开启（自 v3.3 起即默认）
- `experimental.polyfillVueUseHead`：将默认关闭（自 v3.4 起即默认）
- `experimental.respectNoSSRHeader`：将默认关闭（自 v3.4 起即默认）
- `experimental.viteEnvironmentApi`：现在始终启用，且不可禁用

#### 变更原因

这些选项长期默认开启或关闭，目前没有理由保留为可配置状态。

#### 迁移步骤

- `polyfillVueUseHead` 可通过用户插件实现，[示例](https://github.com/nuxt/nuxt/blob/f209158352b09d1986aa320e29ff36353b91c358/packages/nuxt/src/head/runtime/plugins/vueuse-head-polyfill.ts#L10-L11)

### 移除顶层 `generate` 配置项

🚦 **影响级别**：最小

#### 变化内容

Nuxt 4 不再支持顶层的 `generate` 配置，包括其所有属性：

- `generate.exclude` —— 排除预渲染路由
- `generate.routes` —— 指定预渲染路由

#### 变更原因

顶层 `generate` 配置是 Nuxt 2 的遗留，现在优先使用 `nitro.prerender` 配置。

#### 迁移步骤

使用对应的 `nitro.prerender` 配置替代 `generate`：

```diff
export default defineNuxtConfig({
- generate: {
-   exclude: ['/admin', '/private'],
-   routes: ['/sitemap.xml', '/robots.txt']
- }
+ nitro: {
+   prerender: {
+     ignore: ['/admin', '/private'],
+     routes: ['/sitemap.xml', '/robots.txt']
+   }
+ }
})
```

了解更多 Nitro prerender 配置选项。

### 标准化页面组件名称

🚦 **影响级别**：最小

#### 变化内容

当设置 `future.compatibilityVersion` 为 `5`（或启用 `experimental.normalizePageNames`）时，页面组件名称将匹配其路由名称，而不是使用文件名。例如，`pages/foo/index.vue` 组件名将变为 `foo`，而不是 `index`。

#### 变更原因

之前，Vue 会根据文件名赋予组件名，导致多个页面（如 `pages/foo/index.vue` 和 `pages/bar/index.vue`）都拥有组件名 `index`。这会导致 `<KeepAlive>` 结合 `include`/`exclude` 过滤器时效果不可靠，并且需要在每个页面手动添加 `defineOptions({ name: '...' })`。

#### 迁移步骤

如果你依赖当前的组件名（例如在 `<KeepAlive>` 的 `include` 或 `exclude` 列表中），请更新为使用路由名称，而非文件名。

```diff
<template>
  <NuxtPage :keepalive="{
-   include: ['index']
+   include: ['foo']
  }" />
</template>
```

若要禁用此行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizePageNames: false,
  },
})
```
