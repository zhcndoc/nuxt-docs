## 升级 Nuxt

### 最新版本

要将 Nuxt 升级到[最新版本](https://github.com/nuxt/nuxt/releases)，请使用 `nuxt upgrade` 命令。

::code-group{sync="pm"}

```bash [npm]
npx nuxt upgrade
```

```bash [yarn]
yarn nuxt upgrade
```

```bash [pnpm]
pnpm nuxt upgrade
```

```bash [bun]
bun x nuxt upgrade
```

```bash [deno]
deno x nuxt upgrade
```

::

### 夜版发布渠道

要使用最新的 Nuxt 构建版本，并在正式发布前测试新功能，请阅读[夜版发布渠道](/docs/guide/going-further/nightly-release-channel)指南。

## 迁移到 Nuxt 5

Nuxt 5 包含了重大改进和变更。本指南介绍了有哪些变化，以及如何迁移现有的 Nuxt 4 应用。

首先，按照[上方的说明](#升级-nuxt)升级 Nuxt。

Nuxt 5 中的大多数行为都是新的默认行为。对于仍可配置的变更，描述该变更的章节会指出用于恢复 Nuxt 4 行为的选项；对于无法配置的变更，章节会说明这一点。

变更内容如下：

- **Nitro v3**：服务器引擎[基于 h3 v2 和 srvx 重写](/docs/getting-started/upgrade#migration-to-nitro-v3)，并为尚未迁移的服务器代码提供[兼容层](/docs/getting-started/upgrade#nitro-v2-compatibility)
- **服务器导入**：服务器工具来自 [`nuxt/server`](/docs/getting-started/upgrade#server-imports-move-to-nuxtserver)，其中包括[会话辅助函数](/docs/getting-started/upgrade#sessions-come-from-nuxtserver)
- **Vite Environment API**：Vite 插件[按环境注册和配置](/docs/getting-started/upgrade#migration-to-vite-environment-api)
- **Vite 8**：打包器改为使用 [Rolldown，而不是 esbuild 和 Rollup](/docs/getting-started/upgrade#migration-to-vite-8)
- **Nitro 作为 Vite 环境**：使用 `@nuxt/vite-builder` 时，服务器和客户端由[一次 Vite 构建完成](/docs/getting-started/upgrade#nitro-builds-as-a-vite-environment)
- **类型化 `$fetch`**：`$fetch` 和 `useFetch` 现在基于[生成的路由类型](/docs/getting-started/upgrade#typed-fetch-rebuilt-on-generated-route-types)进行类型定义，而非 nitro 的 `InternalApi`
- **不再捆绑 `jiti`**：`nuxt.config`、`modules/` 和层配置现在[由运行时加载](/docs/getting-started/upgrade#jiti-is-no-longer-bundled)
- **移除 `process.*` 类型增强**：TypeScript 不再在 `NodeJS.Process` 上暴露[已弃用的 `process.*` 标志](/docs/getting-started/upgrade#process-type-augmentation-removed)
- **区分大小写的路由**：页面路由[会严格匹配 URL 的大小写](/docs/getting-started/upgrade#case-sensitive-routing)，与 Nitro 保持一致
- **规范化的页面名称**：页面组件名称[与路由名称保持一致](/docs/getting-started/upgrade#normalized-page-component-names)，确保 `<KeepAlive>` 行为一致
- **可序列化的页面元数据**：可静态分析的 `definePageMeta` 值会[写入生成的路由记录](/docs/getting-started/upgrade#serializable-page-meta-extracted-at-build-time)
- **客户端有效负载提取**：[`experimental.payloadExtraction`](/docs/getting-started/upgrade#payload-extraction-defaults-to-client) 的值为 `'client'`，预渲染页面的有效负载会内嵌在 HTML 中
- **`clearNuxtState` 重置为默认值**：`clearNuxtState` 会[将状态重置为初始值](/docs/getting-started/upgrade#respect-defaults-when-clearing-usestate)，而不是将其设为 `undefined`
- **`navigateTo` 提前返回**：顶层的 `await navigateTo()` 成功后会[停止后续 `setup()` 代码的执行](/docs/getting-started/upgrade#early-return-from-navigateto)
- **非异步的 `callHook`**：[`callHook` 可能返回 `void`](/docs/getting-started/upgrade#non-async-callhook)，而不再总是返回 `Promise`
- **注释节点占位符**：仅客户端组件在 SSR 占位时使用[注释节点，而不是 `<div>`](/docs/getting-started/upgrade#client-only-comment-placeholders)，修复了一个作用域样式的水合问题
- **默认关闭服务器自动导入**：服务器代码现在[显式导入 Nitro 的辅助函数](/docs/getting-started/upgrade#server-auto-imports-are-now-opt-in)，而不再依赖自动导入层
- **解析后的 `error.data`**：[`experimental.parseErrorData`](/docs/getting-started/upgrade#experimentalparseerrordata-is-no-longer-configurable) 被强制启用，因此 `error.data` 会以未字符串化的形式传递到错误页面
- **构建器文件监视器**：Nuxt 在开发时[复用构建器自身的监视器](/docs/getting-started/upgrade#builder-file-watcher-in-development)，而不是另行启动一个
- **仅服务器端的 head 组合式函数**：`useServerHead`、`useServerHeadSafe` 和 `useServerSeoMeta`[不再自动导入](/docs/getting-started/upgrade#server-only-head-composables-are-no-longer-auto-imported)，且 `unhead.legacy` 将被忽略
- **默认禁用 Vue Options API**：[Options API 会从客户端包中编译移除](/docs/getting-started/upgrade#vue-options-api-disabled-by-default)，以减小包体积
- **类型化页面**：默认启用 [`experimental.typedPages`](/docs/getting-started/upgrade#typed-pages-enabled-by-default)，支持经过类型检查的路由
- **Node 解析配置类型**：生成的 `node` tsconfig 会描述[运行时如何加载 `nuxt.config` 和模块](/docs/getting-started/upgrade#jiti-is-no-longer-bundled)
- **更严格的副作用导入检查**：生成的 `tsconfig.json` 会启用 [`noUncheckedSideEffectImports`](/docs/getting-started/upgrade#stricter-side-effect-imports)，与 TypeScript 7 的默认设置保持一致
- **忽略 TypeScript `baseUrl`**：生成的 TypeScript 配置[不再使用 `compilerOptions.baseUrl`](/docs/getting-started/upgrade#typescript-baseurl-is-ignored)解析 Nuxt 别名
- **PostCSS 插件**：默认[不再安装或配置 `autoprefixer` 和 `cssnano`](/docs/getting-started/upgrade#postcss-plugins-are-no-longer-installed-by-default)
- **可选依赖**：[`@vitejs/plugin-vue-jsx`](/docs/getting-started/upgrade#vitejsplugin-vue-jsx-is-now-optional) 和 [`giget`](/docs/getting-started/upgrade#giget-is-now-optional-remote-layers) 会按需安装
- **移除的选项**：[若干实验性选项](/docs/getting-started/upgrade#removed-configuration-options)已被移除，因为它们控制的行为现在是无条件启用的

::note
Nuxt 5 仍在开发中，因此随着后续工作推进，本页面也会持续更新。迁移期间请定期回来查看。
::

以下将介绍破坏性或重大变更，以及相应的迁移步骤和可用配置。

### 移除 `process.*` 类型增强

🚦 **影响级别**：最小

#### 变更内容

Nuxt 不再为 `NodeJS.Process` 增强 `browser`、`client`、`dev`、`server` 和 `test` 属性。为兼容性保留了这些标志位的构建时定义，但 TypeScript 不会将它们视为已知属性。

请优先使用 [`import.meta.*`](/docs/api/advanced/import-meta)。这些标志会在构建时替换，并且仍可进行 tree-shaking。

#### 迁移步骤

请在你的应用代码、模块和库中替换旧的检查方式：

```ts
// 之前
// eslint-disable-next-line nuxt/prefer-import-meta
if (process.server) {
  /* ... */
}

// 之后
if (import.meta.server) {
  /* ... */
}
```

[`nuxt/prefer-import-meta`](https://eslint.nuxt.com/packages/plugin#nuxtprefer-import-meta) ESLint 规则会标记仍在使用的 `process.*`。

### 区分大小写的路由

🚦 **影响等级**：最小

#### 变更内容

`router.options.sensitive` 现在默认为 `true`，因此页面路由会区分大小写地匹配 URL，与 Nitro 保持一致。例如，`/About` 不再匹配 `pages/about.vue`。

#### 迁移步骤

更新链接，使其与对应页面路由的大小写保持一致。若要保持不区分大小写的匹配：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  router: {
    options: {
      sensitive: false,
    },
  },
})
```

### 规范化的页面组件名称

🚦 **影响级别**：最小

#### 变更内容

`experimental.normalizePageNames` 现在默认启用，因此页面组件会根据路由命名，而不是根据文件名命名。`pages/foo/index.vue` 和 `pages/bar/index.vue` 分别命名为 `foo` 和 `bar`，而不是都命名为 `index`。

#### 迁移步骤

如果你通过组件名称筛选 `<KeepAlive>`，请将 `include`／`exclude` 更新为路由名称。若要保留基于文件名的命名方式：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    normalizePageNames: false,
  },
})
```

### 在构建时提取可序列化的页面元数据

🚦 **影响级别**：最小

#### 变更内容

`experimental.extractSerializablePageMeta` 现在默认启用。每个可 JSON 序列化的 `definePageMeta()` 属性都会写入生成的路由记录，而不再只处理固定的一组键（以及 `experimental.extraPageMetaExtractionKeys`），并将其余属性留到运行时从每个页面的元数据模块中解析。

值无法序列化的属性（例如函数、变量引用和展开语法）仍会在运行时解析。

#### 迁移步骤

如果你在构建时从路由记录读取页面元数据（例如在 `pages:extend` 钩子中），现在会在那里看到提取后的值。若要保留之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    extractSerializablePageMeta: false,
  },
})
```

### 有效负载提取默认设为 `'client'`

🚦 **影响级别**：最小

#### 变更内容

`experimental.payloadExtraction` 现在默认为 `'client'`，而不是 `true`。预渲染或缓存页面的有效负载会内嵌到首次渲染的 HTML 中，只有在客户端导航时才会请求 `_payload.json` 文件。禁用 `ssr` 时，该选项仍会被强制设为 `false`。

#### 迁移步骤

大多数应用无需更改。如果你会自行请求首次渲染所需的 `_payload.json`，或在测试中测量 HTML 大小，请显式设置此选项：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    payloadExtraction: true,
  },
})
```

::read-more{to="/docs/getting-started/prerendering#payload-extraction"}
进一步了解有效负载提取以及各种模式的影响。
::

### 清除 `useState` 时遵循默认值

🚦 **影响级别**：最小

#### 变更内容

`experimental.defaults.useState.resetOnClear` 现在默认启用，因此 [`clearNuxtState`](/docs/api/utils/clear-nuxt-state) 会将状态重置为 [`useState`](/docs/api/composables/use-state) 的 `init` 函数所返回的值，而不是将其设为 `undefined`。

#### 迁移步骤

如果你的代码在清除状态后会检查 `undefined`，请改为检查初始值。若要保留之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    defaults: {
      useState: {
        resetOnClear: false,
      },
    },
  },
})
```

### `navigateTo` 提前返回

🚦 **影响级别**：最小

#### 变更内容

`experimental.navigateToEarlyReturn` 现在默认启用。在 `<script setup>` 中顶层的 `await navigateTo()` 会被编译为 `setup()` 提前返回；如果导航成功，后续 setup 代码将不会运行，并且组件会在导航进行时渲染一个占位注释。

#### 迁移步骤

如果你依赖成功的 `await navigateTo()` 之后的代码继续运行，请将这些代码移到导航之前。若要保留之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    navigateToEarlyReturn: false,
  },
})
```

### 开发时的构建器文件监视器

🚦 **影响级别**：最小

#### 变更内容

`experimental.watcher` 现在默认为 `'builder'`，因此 Nuxt 会复用当前构建器的文件监视器（例如 Vite 的 `server.watcher`），而不是另行启动一个。如果构建器没有提供监视器，Nuxt 会回退到之前的选择。

#### 迁移步骤

如果你依赖对构建器忽略的文件进行监视，请显式指定一个监视器：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    watcher: 'chokidar',
  },
})
```

### 不再捆绑 `jiti`

🚦 **影响级别**：中等

#### 变更内容

Nuxt 不再依赖 [`jiti`](https://github.com/unjs/jiti)。在打包器之外加载的文件（`nuxt.config.ts`、`modules/` 中的文件以及层配置）现在由运行时本身导入。

**你仍然可以使用 TypeScript 编写配置。** Nuxt 5 要求使用 Node `22.19`、`24.11` 或更高版本，这些版本默认启用类型剥离，因此 `nuxt.config.ts` 和 TypeScript 模块可以原生加载。运行时无法完成、但 `jiti` 过去会代为处理的有两件事：猜测文件扩展名，以及编译会生成代码的 TypeScript 语法。

否则，这两类问题只有在 Nuxt 加载文件时才会暴露出来。因此，现在生成的 `node` tsconfig 会按照运行时实际看到的方式描述环境（将 `module` 和 `moduleResolution` 设置为 `nodenext`，并启用 [`erasableSyntaxOnly`](https://www.typescriptlang.org/tsconfig/#erasableSyntaxOnly)），TypeScript 会提前报告这两类问题。

这只适用于 `nuxt.config`、`modules/` 和层配置。你的应用代码和 `shared/` 代码会经过 Vite，并按照以往的方式解析。如果你需要之前的行为，可以覆盖配置：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    nodeTsConfig: {
      compilerOptions: {
        module: 'preserve',
        moduleResolution: 'bundler',
        erasableSyntaxOnly: false,
      },
    },
  },
})
```

#### 变更原因

过去，Nuxt 会将 `jiti` 引入每个安装中，以加载少量文件，而现在运行时已经可以在没有它帮助的情况下加载其中的大多数文件。移除它可以减小默认安装的体积。

#### 迁移步骤

**1. 为相对导入添加文件扩展名。**

`nuxt.config.ts`、`modules/` 和层配置中的相对导入需要显式指定扩展名：

```diff [nuxt.config.ts]
- import { myPlugin } from './build/my-plugin'
+ import { myPlugin } from './build/my-plugin.ts'
```

TypeScript 会将缺少扩展名报告为 `TS2835`。请注意，它的快速修复建议使用 `./build/my-plugin.js`；应填写文件实际使用的扩展名（`.ts`），Node 会直接解析该扩展名。

裸包导入（`import { defu } from 'defu'`）不受影响。

**2. 使用可擦除的 TypeScript 语法。**

类型注解会被擦除，但会生成运行时代码的语法则无法使用。在配置和模块文件中，将以下写法替换为：

- 将 `enum Foo {}` 替换为 `const` 对象
- 将 `namespace`／`module` 代码块替换为普通导出
- 将构造函数参数属性（`constructor(private x: string) {}`）替换为显式赋值
- 实验性装饰器

TypeScript 会将这些问题报告为 `TS1294`。

**3. 如果你发布的是层或模块，请提供编译后的 JavaScript。**

这一点仅适用于包。无论配置如何，运行时都拒绝从 `node_modules` 中的任何文件剥离类型，因此使用 TypeScript 编写的已发布入口文件无法原生加载，不论 Node 版本有多新。请在发布前编译为 JavaScript；如果你的包包含 `nuxt.config`，请将其输出为 `nuxt.config.mjs`。否则，每个使用该包的项目都必须安装 `jiti`。

这不适用于你自己项目中的层：`layers/*/nuxt.config.ts` 会被原生加载。

**4. 如果仍然需要 `jiti`，请安装它。**

`jiti` 现在是可选的对等依赖。安装后，只要运行时无法自行加载某个文件，Nuxt 就会自动将其作为回退方案使用：

::code-group{sync="pm"}

```bash [npm]
npm i -D jiti
```

```bash [yarn]
yarn add -D jiti
```

```bash [pnpm]
pnpm add -D jiti
```

```bash [bun]
bun add -D jiti
```

::

无论使用哪个 Node 版本，`nuxt.schema` 文件始终需要 `jiti`：其中的 JSDoc 注解是通过导入时转换读取的，而不是通过导入文件本身读取的。

此外还有一项较小的变更：`postcss.plugins` 中指定的 PostCSS 插件现在由运行时解析，因此，仅能通过 Nuxt `alias` 条目解析的插件名称将不再加载。请使用包名称或路径。

### 迁移到 Vite 环境 API

🚦 **影响级别**：中等

#### 变更内容

Nuxt 5 迁移到 Vite 6 的新[环境 API](https://vite.dev/guide/api-environment)，该 API 正式化了环境的概念，并提供了对每个环境配置的更好控制。

之前，Nuxt 使用单独的客户端和服务器 Vite 配置。现在，Nuxt 使用共享的 Vite 配置，并配备特定于环境的插件，这些插件使用 `applyToEnvironment()` 方法来针对特定环境。

::note
Vite 环境 API 在 Nuxt 5 中始终启用。`experimental.viteEnvironmentApi` 选项已被移除。
::

**关键变化：**

1. **不再支持特定于环境的 `extendViteConfig()`**：`extendViteConfig()` 中的 `server` 和 `client` 选项已被弃用，使用时将显示警告。

2. **更改插件注册**：使用 `addVitePlugin()` 注册的 Vite 插件，如果仅针对一个环境（通过传递 `server: false` 或 `client: false`），将不会调用其 `config` 或 `configResolved` 钩子。

3. **共享配置**：`vite:extendConfig` 和 `vite:configResolved` 钩子现在与共享配置一起工作，而不是单独的客户端／服务器配置。

#### 变更原因

Vite 环境 API 提供了：
- 更好的一致性，确保开发和生产构建之间的差异最小化
- 更细粒度的环境特定配置控制
- 改进的性能和插件架构
- 支持自定义环境，而不仅仅是客户端和服务器

#### 迁移步骤

##### 1. 迁移到使用 Vite 插件

我们建议您使用 Vite 插件，而不是 `extendViteConfig`、`vite:configResolved` 和 `vite:extendConfig`。

```ts
// 之前
extendViteConfig((config) => {
  config.optimizeDeps.include.push('my-package')
}, { server: false })

nuxt.hook('vite:extendConfig' /* 或 vite:configResolved */, (config, { isClient }) => {
  if (isClient) {
    config.optimizeDeps.include.push('my-package')
  }
})

// 之后
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // 这里可以设置全局 vite 配置
  },
  configResolved (config) {
    // 这里可以访问完整解析后的 vite 配置
  },
  configEnvironment (name, config) {
    // 这里可以设置特定环境的 vite 配置
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

##### 2. 迁移 Vite 插件以使用环境

您可以使用插件中的新 `applyToEnvironment` 钩子，而不是使用 `addVitePlugin` 结合 `server: false` 或 `client: false`。

```ts
// 之前
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    config.optimizeDeps.include.push('my-package')
  },
}), { client: false })

// 之后
addVitePlugin(() => ({
  name: 'my-plugin',
  config (config) {
    // 这里可以设置全局 vite 配置
  },
  configResolved (config) {
    // 这里可以访问完整解析后的 vite 配置
  },
  configEnvironment (name, config) {
    // 这里可以设置特定环境的 vite 配置
    if (name === 'client') {
      config.optimizeDeps ||= {}
      config.optimizeDeps.include ||= []
      config.optimizeDeps.include.push('my-package')
    }
  },
  applyToEnvironment (environment) {
    return environment.name === 'client'
  },
}))
```

::read-more{to="https://vite.dev/guide/api-environment" target="_blank"}
进一步了解 Vite 环境 API

### 迁移到 Vite 8

🚦 **影响级别**：中等

#### 变更内容

Nuxt 5 从 Vite 7 升级到 [Vite 8](https://main.vite.dev/guide/migration)，其中用 [Rolldown](https://rolldown.rs) 替换了 esbuild 和 Rollup 作为底层打包器。这带来显著更快的构建速度，但包含若干破坏性更改。

::note
没有可供切换的选项：Nuxt 5 要求使用 Vite 8。如果你想先在 Nuxt 4 上测试 Vite 8 的兼容性，可以在 `package.json` 中添加 `"vite": "^8.3.0"` resolution override。

大多数迁移由 Nuxt 内部处理，但有些面向用户的变化需要关注：

- `vite.esbuild` 和 `vite.optimizeDeps.esbuildOptions` 已弃用，替换为 `vite.oxc` 和 `vite.optimizeDeps.rolldownOptions`。Vite 8 目前会自动转换这些选项，但未来将移除旧选项。
- `build.rollupOptions` 已弃用，请改用 `build.rolldownOptions`。
- CommonJS 互操作行为发生变化。如果使用 CJS 模块，请查阅 [Vite 8 迁移指南](https://main.vite.dev/guide/migration#consistent-commonjs-interop)。

::read-more{to="https://main.vite.dev/guide/migration" target="_blank"}
查看完整的 Vite 8 迁移指南及破坏性更改
::

### Nitro 作为 Vite 环境构建

🚦 **影响级别**：中等

#### 变更内容

使用 `@nuxt/vite-builder` 时，`experimental.nitroViteEnvironment` 现在默认为 `true`，因此 Nitro 会通过 `nitro/vite` 插件作为 [Vite 环境](https://vite.dev/guide/api-environment)构建，而不再使用 Nitro 自身的 Rolldown 流程。服务器和客户端由一次 Vite 构建完成，服务器代码也会经过应用代码已使用的 Vite 插件和解析流程。

此选项对其他应用构建器无效，这些构建器仍会使用 Nitro 自身的流程。在这些构建器中将该选项设为 `true` 会记录警告。

#### 迁移步骤

直接配置 Nitro 打包器的模块（例如通过 `nitro.rollupConfig`）会遇到服务器构建不再运行的流程。请改为注册 Vite 插件，并使用 `applyToEnvironment` 指定适用范围。

若要保留 Nitro 自身的构建流程：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    nitroViteEnvironment: false,
  },
})
```

### 服务器导入改为来自 `nuxt/server`

🚦 **影响级别**：中等

#### 变更内容

Nuxt 5 提供了 `nuxt/server`，用于导入服务器代码最常用的服务器工具：`defineEventHandler`、`createError`、`getQuery`、`readBody`、cookie 和 header 辅助函数、`sendRedirect`、`getRouteRules` 以及 `useRuntimeConfig`。它取代了已弃用的 `@nuxt/nitro-server/h3`。

应用所使用的服务器运行时取决于配置的 [`server.builder`](/docs/guide/going-further/builders)，而从 `nitro/h3` 导入会将代码固定到其中一种运行时及其主版本。`nuxt/server` 则不会，因此同一个文件可以用于 Nuxt 4.6（运行 `nitropack` v2 或 Nitro v3）和 Nuxt 5。

```diff [server/api/hello.ts]
- import { defineEventHandler, getQuery } from 'nitro/h3'
+ import { defineEventHandler, getQuery } from 'nuxt/server'

  export default defineEventHandler((event) => {
    return getQuery(event)
  })
```

错误的形式与应用 Vue 部分创建的错误相同，并且来自同一处：

```diff
- import { HTTPError } from 'nitro/h3'
+ import { createError } from 'nuxt/server'

  export default defineEventHandler(() => {
-   throw new HTTPError({ status: 400, statusText: 'Bad request' })
+   throw createError({ status: 400, statusText: 'Bad request' })
  })
```

服务器自动导入也会解析到 `nuxt/server`，因此保留自动导入的项目无需更改。

#### 迁移步骤

1. 将 `nitro/h3` 和 `@nuxt/nitro-server/h3` 导入替换为 `nuxt/server`，适用于[该导入接口](/docs/guide/going-further/server-imports#types-and-utilities)中的工具。
2. 其他内容仍使用 `nitro/h3`。`nuxt/server` 并不是 h3 的重新导出，因此 `readValidatedBody` 和 `handleCors` 等辅助函数仍应从原处导入。
3. 从 `event` 上访问的内容都无需更改：在默认 Nitro 构建器下，它仍然是 h3 的 `H3Event`。

::read-more{to="/docs/guide/going-further/server-imports"}
了解该导入接口涵盖的内容，以及它对模块作者的意义。
::

### 会话辅助函数来自 `nuxt/server`

🚦 **影响级别**：中等

#### 变更内容

`useSession`、`getSession`、`updateSession` 和 `clearSession` 现在属于 [`nuxt/server`](/docs/guide/going-further/server-imports#sessions)，自动导入的同名标识符也会解析到这里。它们使用 `iron-webcrypto` 在符合 Web 标准的 `Request` 和 `Response` 上封装会话，因此可以在任何 [`server.builder`](/docs/guide/going-further/builders) 下运行，而不仅限于 Nitro。

由 h3 辅助函数签发的会话无法通过这些函数解封，默认 cookie 名称也从 `h3` 改为 `nuxt-session`。所有在升级前已登录的用户都会获得一个新的空会话一次。

现在不再需要 `password`。未提供密码时，会话会使用从 [`appSecret`](/docs/guide/going-further/runtime-config#application-secret) 派生的密钥进行封装，该密钥由 `NUXT_APP_SECRET` 设置：

```diff [server/api/me.ts]
  export default defineEventHandler(async (event) => {
-   const session = await useSession<{ user?: string }>(event, {
-     password: process.env.NUXT_SESSION_PASSWORD!,
-   })
+   const session = await useSession<{ user?: string }>(event)
    return { user: session.data.user }
  })
```

仍可传入至少 32 个字符的 `password`，并使用它进行封装。

若要保留 h3 的实现，请显式导入：

```diff [server/api/me.ts]
+ import { useSession } from 'nitro/h3'

  export default defineEventHandler(async (event) => {
    const session = await useSession(event, { password: process.env.NUXT_SESSION_PASSWORD! })
    return { user: session.data.user }
  })
```

#### 迁移步骤

1. 请做好现有会话失效的准备：升级部署后，用户会退出登录一次。
2. 如果你依赖 h3 特有的选项（`sessionHeader`、`crypto`、`seal`），请从 `nitro/h3` 导入 `useSession`，或改用 `nuxt/server` 中对应的选项：`name`、`maxAge` 和 `cookie`。
3. 如果移除了 `password`，请在每个部署环境中设置 `NUXT_APP_SECRET`；在开发环境中，Nuxt 会生成一个密钥。
4. 仅当你同时保留 h3 辅助函数时，才将 cookie 名称设为 `h3`；两种实现不应共用同一个 cookie。

::read-more{to="/docs/guide/going-further/server-imports#sessions"}
了解会话辅助函数涵盖的内容。
::

### 迁移到 Nitro v3

🚦 **影响级别**：重大

#### 发生了什么变化

Nuxt 5 升级到了 [Nitro v3](https://nitro.build/blog/v3-beta)，这是服务器引擎的一次重大重写。Nitro v3 基于 [srvx](https://srvx.h3.dev) 和 [h3 v2](https://h3.dev) 构建，全面采用 Web 标准的 `Request`／`Response` API。这带来了性能提升和更一致的 API，但服务器端代码存在若干破坏性变更。

::important
我们仍在继续完善 Nitro v3 集成，因此你应预期会有更多变化，以及额外工作来让迁移更加顺利。
::

::read-more{to="https://nitro.build/blog/v3-beta" target="_blank"}
阅读 Nitro v3 测试版公告以获取完整概览。
::

::read-more{to="https://nitro.build/docs/migration" target="_blank"}
查看完整的 Nitro v3 迁移指南以了解所有破坏性变更。
::

以下章节重点介绍与 Nuxt 应用开发者和模块作者最相关的变化。升级前无需完成所有迁移：请参阅 [Nitro v2 兼容性](#nitro-v2-compatibility)，了解可在过渡期间让旧服务器代码继续运行的兼容层。

#### 包及导入路径变化

`nitropack` 包更名为 `nitro`。所有导入路径都发生了变化：

| 之前 | 之后 |
|---|---|
| `nitropack` | `nitro` |
| `nitropack/types` | `nitro/types` |
| `nitropack/runtime` | `nitro` |
| `h3`（用于服务器工具） | `nitro/h3` |

如果服务器代码中有显式导入，请更新它们：

```diff
- import { defineEventHandler, getQuery } from 'h3'
+ import { defineEventHandler, getQuery } from 'nitro/h3'
```

**模块作者请注意**，类型扩展必须针对新的模块路径：

```diff
- declare module 'nitropack/types' {
+ declare module 'nitro/types' {
    interface NitroRuntimeConfig {
      myModule?: { /* ... */ }
    }
  }
```

路由规则会扩展另一个模块。请参阅[路由规则类型改为来自 `h3/rules`](#route-rule-types-move-to-h3rules)。

#### 服务器自动导入现已改为选择启用

Nitro v3 移除了自动导入支持，因此 `defineEventHandler`、`getQuery`、`readBody` 和 `useRuntimeConfig` 等工具不再是服务器代码中的全局标识符。Nuxt 仍会提供它们，但在 Nuxt 5 中默认关闭。

请在服务器代码中添加显式导入。优先使用 [`nuxt/server`](/docs/guide/going-further/server-imports)，自动导入也会解析到此处：

```diff [server/api/hello.ts]
+ import { defineEventHandler, getQuery } from 'nuxt/server'
+
  export default defineEventHandler((event) => {
    return getQuery(event)
  })
```

或者，在迁移期间保留之前的行为：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    nitroAutoImports: true,
  },
})
```

这仅适用于 Nitro 和 h3 提供的工具。你在 `server/utils/` 和 `shared/utils/` 中的自有导出仍会自动导入。

#### 服务器代码中的 `#imports` 已弃用，应改用 `#imports/server`

服务器代码应从 `#imports/server` 导入：

```diff [server/api/hello.ts]
- import { defineEventHandler } from '#imports'
+ import { defineEventHandler } from '#imports/server'

  export default defineEventHandler(() => ({ hello: true }))
```

服务器代码运行时，`#imports` 仍可解析，因此尚未迁移的项目仍可正常运行，但它不再有类型定义：在迁移到 `#imports/server` 之前，TypeScript 会将其报告为无法解析。

#### 错误处理：使用 `status`／`statusText` 替代 `statusCode`／`statusMessage`

h3 v2 重命名了错误属性以符合 Web 标准：

```diff
  createError({
-   statusCode: 404,
-   statusMessage: 'Not Found',
+   status: 404,
+   statusText: 'Not Found',
  })
```

在服务器路由中，错误类由 `createError` 变为 `HTTPError`：

```diff
- import { createError } from 'h3'
+ import { HTTPError } from 'nitro/h3'

  export default defineEventHandler(() => {
-   throw createError({ statusCode: 400, statusMessage: 'Bad request' })
+   throw new HTTPError({ status: 400, statusText: 'Bad request' })
  })
```

::note
在应用的 Vue 部分（`app/` 目录），Nuxt 的 `createError` 组合式函数依旧可用，并且推荐用于抛出错误。
::

#### `createError` 不再返回 `HTTPError` 实例

`NuxtError` 现在是独立的类，而不是 h3 的 `HTTPError` 子类，因此，使用 Nuxt 的 `createError` 创建的错误不再匹配 `instanceof HTTPError`。其他方面均未变化：错误保留相同的属性，以相同的方式进行序列化，并且在 SSR 期间仍会映射到正确的 HTTP 响应。

如果按类缩小错误类型范围，请改用以下谓词之一：

```diff
- if (error instanceof HTTPError) {
+ if (HTTPError.isError(error)) {
    // 同时处理 `new HTTPError()` 和 Nuxt 的 `createError()`
  }
```

```diff
+ import { isNuxtError } from '#app'
+
+ if (isNuxtError(error)) {
+   // 将错误类型缩小为使用 Nuxt 的 `createError` 创建的错误
+ }
```

#### 服务器事件 API 变更（h3 v2）

`H3Event` 对象现采用 Web 标准 API：

**请求属性：**
```diff
- event.path              // 字符串
+ event.url.pathname      // URL 对象 - 使用 .pathname，.search，.hash

- event.method            // 字符串
+ event.req.method        // 通过 Web Request 对象

- event.node.req.headers  // Node.js IncomingHttpHeaders
+ event.req.headers       // Web Headers API（.get()、.set()、.has()）
```

**响应属性：**
```diff
- event.node.res.statusCode = 200
+ event.res.status = 200

- event.node.res.statusMessage = 'OK'
+ event.res.statusText = 'OK'

- setResponseHeader(event, 'x-custom', 'value')
+ event.res.headers.set('x-custom', 'value')

- appendResponseHeader(event, 'set-cookie', cookie)
+ event.res.headers.append('set-cookie', cookie)
```

#### `useRuntimeConfig()` 不再接受 `event`

在 Nitro v3 中，`useRuntimeConfig()` 在服务器路由中不再需要（也不接受）传入 `event` 参数：

```diff
  export default defineEventHandler((event) => {
-   const config = useRuntimeConfig(event)
+   const config = useRuntimeConfig()
  })
```

#### 路由规则：`statusCode` 重命名为 `status`

如果定义了重定向路由规则，属性名称发生了变化：

```diff
  export default defineNuxtConfig({
    routeRules: {
      '/old-page': {
-       redirect: { to: '/new-page', statusCode: 302 },
+       redirect: { to: '/new-page', status: 302 },
      },
    },
  })
```

Nuxt 目前会将 `statusCode` 应用为 `status` 并发出警告，因此，尚未迁移的规则仍会保留其状态码，而不会静默回退到默认值。该回退处理将被移除。

#### 缓存路由规则忽略查询参数

缓存路由（`cache`、`swr`、`isr`）现在仅根据路径生成键，并会在处理程序运行前删除查询字符串。将 `allowQuery` 设为 `true` 或参数名称列表即可保留查询字符串：

```ts
export default defineNuxtConfig({
  routeRules: {
    '/products': { cache: { swr: true, maxAge: 60, allowQuery: ['page'] } },
  },
})
```

#### 路由规则类型改为来自 `h3/rules`

Nitro v3 基于 h3 构建路由规则，因此自定义路由规则应在该处声明，而不是在 `nitro/types` 上声明。`NitroRouteConfig` 和 `NitroRouteRules` 仍作为已弃用的别名导出，但它们现在是类型别名，而不是接口，因此扩展它们会报错：`TS2300: Duplicate identifier`。

需要声明两个接口，并且它们有意保持分离。`RouteRuleConfig` 表示 `nuxt.config` 中的规则，`RouteRules` 表示运行时匹配到的规则：

```diff
- declare module 'nitropack/types' {
-   interface NitroRouteConfig {
+ declare module 'h3/rules' {
+   interface RouteRuleConfig {
      myModule?: { enabled: boolean }
    }
-   interface NitroRouteRules {
+   interface RouteRules {
      myModule?: { enabled: boolean }
    }
  }
```

未声明规则现在读取到的是 `unknown`，而不再是 `any`，因此需要在使用位置进行类型断言：

```diff
- const enabled = rules.myUndeclaredRule
+ const enabled = rules.myUndeclaredRule as boolean | undefined
```

#### 服务器 `tsconfig.json` 现在由 Nuxt 生成

Nuxt 现在会自行生成 `.nuxt/tsconfig.server.json`，将其作为按环境写入的 tsconfig 之一，而不是委托服务器构建器生成。如果你通过 Nitro 扩展了它，请改用 Nuxt 选项：

```diff
  export default defineNuxtConfig({
-   nitro: {
-     typescript: {
-       tsConfig: { compilerOptions: { /* ... */ } },
-     },
-   },
+   typescript: {
+     serverTsConfig: { compilerOptions: { /* ... */ } },
+   },
  })
```

`typescript.serverTsConfig` 在 Nuxt 4 中已经存在，并会与 `nitro.typescript.tsConfig` 保持同步，因此如果你已经在使用它，这项变更不会产生影响。

#### 模块作者注意：其他变更

- **Nitro 插件导入**：使用 `import { definePlugin } from 'nitro'`，现在默认要求这样做。请参阅[服务器自动导入现已改为选择启用](#server-auto-imports-are-now-opt-in)。
- **路由规则辅助函数**：`basicAuth` 路由规则已由中间件取代，新的 `cors` 规则取代了手动配置 CORS。运行时相关详情请参阅 [Nitro 迁移指南](https://nitro.build/docs/migration)。
- **运行时钩子**：`nitroApp.hooks.hook('beforeResponse', ...)` 和 `nitroApp.hooks.hook('afterResponse', ...)` 已由 `nitroApp.hooks.hook('response', ...)` 取代。
- **来自 `nitro/app` 的 `getRouteRules()`**：在服务器端，Nitro 辅助函数从 `getRouteRules(event)` 改为 `getRouteRules(method, pathname)`，并返回 `{ routeRules }`。

### 移除 `experimental.externalVue`

🚦 **影响级别**：极小

#### 变更内容

`experimental.externalVue` 选项已被移除。当未启用 `vue.runtimeCompiler` 时，Vue 编译器依赖（`@babel/parser`、`@vue/compiler-core`、`@vue/compiler-dom`、`@vue/compiler-ssr`、`estree-walker`）现在始终在服务器包中被替换为模拟代理。

#### 变更原因

随着迁移到 Nitro v3，所有依赖项默认都会打包到服务器输出中（不像 Nitro v2 那样将 `node_modules` 外部化）。`externalVue` 选项最初设计用于将 Vue 保持为外部依赖，这是为了避免打包多个 Vue 副本，但由于 Nitro v3 无论如何都会打包所有内容，该选项变得无效。

Vue 的服务器构建包含完整的编译器工具链，会不必要地将 `@babel/parser`（465KB）和其他编译器包拉入服务器包中。这些编译器包仅在启用 `vue.runtimeCompiler` 进行运行时模板编译时才需要。

通过始终模拟这些编译器依赖，默认服务器包大小减少了约 860KB（约 59%）。

#### 迁移步骤

如果你之前显式设置了 `experimental.externalVue`，现在应该将其移除。

```diff
  export default defineNuxtConfig({
    experimental: {
-     externalVue: false,
    },
  })
```

::note
如果你使用 `vue.runtimeCompiler: true`，真正的编译器包仍会像以前一样包含在内。
::

### 仅服务器端的 head 组合式函数不再自动导入

🚦 **影响级别**：最小

#### 变更内容

`useServerHead`、`useServerHeadSafe` 和 `useServerSeoMeta` 已从 Nuxt 的自动导入中移除。它们仍从 `#app` 导出，因此显式导入后仍可使用。

Nuxt 5 会忽略 `unhead.legacy` 选项：设置该选项会记录警告。Unhead 的旧版插件（`DeprecationsPlugin`、`PromisesPlugin`、`AliasSortingPlugin`）不再注册，并且始终启用 Capo 排序。`TemplateParamsPlugin` 仍会注册，因此 `%s`、`%siteName` 和 `%separator` 标题插值不受影响。

仅服务器端的 head 组合式函数从客户端包中进行 tree-shaking，由 `@unhead/vue/vite` 插件处理；使用 `@nuxt/vite-builder` 时，Nuxt 会注册该插件。

#### 迁移步骤

改为在 `import.meta.server` 中调用 `useHead`，或显式导入组合式函数：

```diff
+ import { useServerHead } from '#app'
+
  useServerHead({ meta: [{ name: 'generator', content: 'Nuxt' }] })
```

从配置中移除 `unhead.legacy`：

```diff
  export default defineNuxtConfig({
-   unhead: {
-     legacy: true,
-   },
  })
```

### `experimental.parseErrorData` 不再可配置

🚦 **影响级别**：极小

#### 变更内容

`experimental.parseErrorData` 选项已弃用并被强制启用。将其设为 `false` 会记录一条警告，并且除此之外会被忽略，因此错误页面上的 `error.data` 始终是你传递给 `createError` 的值。没有可以关闭它的开关。

#### 变更原因

当 Nuxt 渲染错误页面时，会在内部请求 `/__nuxt_error`，并将错误随请求一起传递。过去，错误会被拆分到每个字段对应的查询参数中，而由于查询参数的值始终是字符串，`error.data` 会以字符串形式传递到页面，并且必须重新解析。`parseErrorData` 就是为了选择退出这一步解析而存在的。

现在，错误会作为单个经过 JSON 编码的参数发送，因此 `error.data` 会保留其原始结构，不再被字符串化。值的类型也会保留，因此 `status` 是数字，布尔值也会保持为布尔值，而不是字符串 `'true'` 和 `'false'`。由于不再有任何逻辑会将 `error.data` 字符串化，该选项仅为仍然期望字符串的应用保留，以便重新将其字符串化。

#### 迁移步骤

移除该选项：

```diff
  export default defineNuxtConfig({
    experimental: {
-     parseErrorData: false,
    },
  })
```

如果你设置它为 `false` 是为了自行解析 `error.data`，也请移除相应的解析逻辑，因为现在 `error.data` 会保留你传递给 `createError` 的值：

```diff
  <script setup lang="ts">
  import type { NuxtError } from '#app'

  const props = defineProps({
    error: Object as () => NuxtError
  })

- const data = JSON.parse(props.error.data)
+ const data = props.error.data
  </script>
```

### `giget` 现在是可选依赖（远程层）

🚦 **影响级别**：极小

#### 变更内容

`giget` 不再默认安装。现在它是 `@nuxt/kit` 的可选对等依赖，仅在需要下载通过远程 URL 指定的 `extends` 层时才需要：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['github:my-org/my-theme'],
})
```

本地层、位于 `~~/layers/` 中的层，以及作为软件包安装的层不受影响。

#### 变更原因

大多数项目从不扩展远程来源，因此为所有项目安装下载器，只是为了服务少数项目。此外，在配置解析时下载层，是使用层时最不可复现的方式：获取过程发生在包管理器之外，因此不会记录在锁文件中；除非手动固定版本，否则也不会固定到某个修订版本。

#### 迁移步骤

**推荐方式：将层移入 `package.json`。** 所有主流包管理器都支持 Git URL，因此远程层可以作为普通依赖。这样它会记录在锁文件中，固定到精确的提交，并与其他依赖一起安装：

```json [package.json]
{
  "devDependencies": {
    "my-theme": "github:my-org/my-theme#4a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b"
  }
}
```

然后通过包名扩展它：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['my-theme'],
})
```

`#` 后面的部分可以是任意 commit-ish，因此标签（`#v1.2.0`）或 `#semver:^1.2.0` 也同样适用；只有完整的提交 SHA 才是真正不可变的形式。

**否则，请安装 `giget`**，并继续使用远程 `extends` 条目：

::code-group{sync="pm"}

```bash [npm]
npm install -D giget
```

```bash [yarn]
yarn add -D giget
```

```bash [pnpm]
pnpm add -D giget
```

```bash [bun]
bun add -D giget
```

::

如果在未安装 `giget` 的情况下解析远程层，Nuxt 会报告具体哪个 `extends` 条目需要它。

### 移除旧版 `_renderResponse` 支持

🚦 **影响级别**：极小

#### 发生了什么变化

不再支持对 `ssrContext._renderResponse` 的兼容回退检测。现在仅使用 Nuxt 导航组合函数设置的内部 `ssrContext['~renderResponse']`。

#### 变更原因

`ssrContext` 上的 `_renderResponse` 属性在内部 API 迁移到 `~renderResponse`（见 [#33896](https://github.com/nuxt/nuxt/pull/33896)）后，仅作为兼容回退保留。TODO 注释指出应在 Nuxt v5 中移除。

#### 迁移步骤

如果你之前直接设置过 `ssrContext._renderResponse`（这从未是公开 API），请改用 `ssrContext['~renderResponse']`。Nuxt 导航组合函数已使用新属性，因此如果你使用 `navigateTo` 或路由中间件，则无需更改。

### 非异步 `callHook`

🚦 **影响级别**：极小

#### 变化内容

升级到 [hookable v6](https://github.com/unjs/hookable) 后，`callHook` 现在可能返回 `void`，而非一直返回 `Promise<void>`。这是一项性能改进，可在没有钩子或仅有同步钩子的情况下避免不必要的 Promise 分配。

Nuxt 4 使用 `Promise.resolve()` 包装了 `callHook`，以便现有的 `.then()` 和 `.catch()` 链式调用继续正常工作。现在已移除该包装，并且 `experimental.asyncCallHook` 现在默认设为 `false`。

::tip
此变动影响构建时的 Nuxt 钩子（模块使用）和运行时的钩子（应用代码中使用）。
::

#### 变更原因

Hookable v6 避免不必要的 Promise 创建，使钩子调用速度提高 20–40 倍，利于有大量钩子的应用。

#### 迁移步骤

如果你（或你使用的模块）在 `callHook` 上使用 `.then()` 或 `.catch()`，请改用 `await`：

```diff
- nuxtApp.callHook('my:hook', data).then(() => { ... })
+ await nuxtApp.callHook('my:hook', data)
```

```diff
- nuxtApp.hooks.callHook('my:hook', data).catch(err => { ... })
+ try { await nuxtApp.hooks.callHook('my:hook', data) } catch (err) { ... }
```

若要让 `callHook` 始终返回 `Promise`：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    asyncCallHook: true,
  },
})
```

### 客户端专属注释占位符

🚦 **影响级别**：极小

#### 变化内容

仅客户端组件（`.client.vue` 文件和 `createClientOnly()` 包装器）现在会在服务端渲染为 HTML 注释（`<!--placeholder-->`），而不是空的 `<div>` 元素。

- 在 `nuxt.config.ts` 的 `modules` 数组中定义的模块
- `modules/` 目录中自动发现的模块

当占位符 `<div>` 与实际组件根元素共享相同标签名时，Vue 运行时在激活期间会跳过重新应用 `setScopeId`。这会导致组件挂载后作用域样式丢失。使用注释节点可完全避免标签名冲突。

此改动确保：

如果你依赖占位符 `<div>` 来继承属性（`class`、`style` 等）以用于布局（例如，预留空间防止布局偏移），请将组件包装在 `<ClientOnly>` 中并添加 `#fallback` 插槽：

```diff
- <MyComponent class="placeholder" style="min-height: 200px" />
+ <ClientOnly>
+   <MyComponent />
+   <template #fallback>
+     <div class="placeholder" style="min-height: 200px"></div>
+   </template>
+ </ClientOnly>
```

若要恢复到之前的 `<div>` 占位符行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    clientNodePlaceholder: false,
  },
})
```

### 更严格的副作用导入

🚦 **影响级别**：最小

#### 变更内容

Nuxt 生成的 `tsconfig.json` 会启用 [`noUncheckedSideEffectImports`](https://www.typescriptlang.org/tsconfig/#noUncheckedSideEffectImports)。这是 TypeScript 7 的默认设置，因此提前采用可让你的项目在升级前与之保持一致。

启用此选项后，TypeScript 无法解析到模块的仅副作用导入（`import './setup'`）现在会变成类型错误，而之前会被忽略。这只影响类型检查（`nuxt typecheck` 和你的编辑器），不影响运行时行为。

#### 变更原因

未解析的副作用导入以前会被静默忽略，因此拼写错误或被删除的文件仍可能通过类型检查。对它们进行标记可以捕获这些错误，并与 TypeScript 7 的默认行为保持一致。

#### 迁移步骤

如果类型检查现在对一个非代码资源的副作用导入报错（例如 `import '~/assets/styles.css'`），请添加一个环境模块声明，让 TypeScript 知道该导入是有效的：

```ts [types.d.ts]
declare module '*.css' {}
```

::tip
你可以通过在 `nuxt.config` 中禁用该选项来恢复到之前的行为：

<!-- @case-police-ignore tsConfig -->

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  typescript: {
    tsConfig: {
      compilerOptions: {
        noUncheckedSideEffectImports: false,
      },
    },
  },
})
```
:: เครดิตฟรี

### 默认禁用 Vue Options API

🚦 **影响级别**：最小

#### 变更内容

Nuxt 将 Vue 的 [`__VUE_OPTIONS_API__`](https://vuejs.org/api/compile-time-flags#VUE_OPTIONS_API) 功能标志设为 `false`，从而将 Vue 的 Options API 运行时从客户端 bundle 中编译移除。

#### 变更原因

尽管大多数 Nuxt 应用都使用 Composition API 和 `<script setup>` 编写，但 Options API 运行时仍会被打包进每个客户端 bundle。移除它可以缩减客户端 bundle（在一个最小应用中约可减少 6 kB 压缩前体积 / 2 kB gzip 后体积）。

#### 迁移步骤

如果你的任何组件（或某个依赖的组件）使用了 Options API（`export default { data() {}, methods: {}, ... }`），请在你的 `nuxt.config` 中重新启用它：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  vue: {
    optionsApi: true,
  },
})
```

::note
`defineNuxtComponent` 不受影响：它的 `asyncData` 和 `head` 选项是通过 `setup()` 处理的，而不是通过 Vue Options API，因此无论该标志如何设置都可以正常工作。
::

### 默认启用类型化页面

🚦 **影响级别**：最小

#### 变更内容

`experimental.typedPages` 现在默认启用。Nuxt 会根据你的 `pages/` 目录生成类型化路由名称和路径，因此 `useRoute`、`navigateTo`、`<NuxtLink>` 和 `router.push` 等组合函数会根据你的实际路由进行类型检查。

#### 变更原因

类型化路由可以在类型检查阶段而不是运行时捕获失效链接和过时的路由名称，而且它现在已经成为 `vue-router` 的原生能力，因此作为默认设置是合理的。

#### 迁移步骤

如果你引用了不存在的路由（例如 `to` 属性中的拼写错误，或者在 `pages/` 目录外动态定义的路由），类型检查现在会报错。请修正该引用，或者为你在运行时添加的路由扩展生成的路由类型。

若要选择退出并恢复到之前的行为：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    typedPages: false,
  },
})
```

### 基于生成的路由类型重建类型化 `$fetch`

🚦 **影响级别**：中等

#### 变化内容

`$fetch` 和 `useFetch` 的类型现在来自 Nuxt 的服务器构建器报告的路由，而不是来自 nitro 的 `InternalApi` 接口。除了响应类型外，匹配的处理程序所验证的 `body`、`query` 或 `headers` 现在也会在调用时受到约束，并且不支持该路由的方法会被拒绝。

由此会产生两项变化：

- 通过手动扩展 nitro 的 `InternalApi` 添加的路由不再会被识别。请改为扩展 `@nuxt/schema` 中的 `ServerRoutes`。
- `$fetch` 或 `useFetch` 不再接受 `params` 选项。它以前是 `query` 的别名。

如果生成的路由类型未描述某个路径，它仍会解析为 `unknown`，除非你选择启用 [`experimental.strictRouteTypes`](/docs/guide/going-further/experimental-features#strictroutetypes)。

#### 变更原因

Nitro v3 移除了类型化 fetch，而旧实现无法扩展到约 300 条以上的路由。无论路由数量多少，新生成的路由类型所需的类型检查成本都相同，并且包含足够的信息来对请求和响应进行类型化。移除 `params` 是为了将该名称留给未来的命名路由参数使用。

#### 迁移步骤

将任何 `params` 选项移至 `query`：

```diff
  const { data } = await useFetch('/api/search', {
-   params: { q: 'nuxt' },
+   query: { q: 'nuxt' },
  })
```

将任何从 `InternalApi` 手动扩展的路由移至 `ServerRoutes`：

```diff [shared/server-routes.d.ts]
- declare module 'nitropack' {
-   interface InternalApi {
-     '/api/hello': { get: { message: string } }
-   }
- }
+ import type { Endpoint } from 'nuxt/app'
+
+ declare module '@nuxt/schema' {
+   interface ServerRoutes {
+     '/api/hello': {
+       [Endpoint]: {
+         GET: { response: { message: string } }
+       }
+     }
+   }
+ }
```

::read-more{to="/docs/getting-started/data-fetching#typed-routes"}
了解更多关于类型化路由的信息。
::

### 忽略 TypeScript `baseUrl`

🚦 **影响级别**：最小

#### 变更内容

Nuxt 会从生成的 TypeScript 配置中移除 `compilerOptions.baseUrl`。相对 Nuxt 和 Nitro 别名现在会从 Nuxt 的构建目录解析，而不是从自定义 `baseUrl` 解析。

#### 变更原因

TypeScript 6 弃用了 `baseUrl`，使用 `paths` 时也不再需要它。移除该选项还可以确保 Nuxt 生成的别名始终以包含这些别名的生成配置为基准。

#### 迁移步骤

从 Nuxt TypeScript 配置中移除 `baseUrl`。如果你使用它来确定相对 Nuxt 或 Nitro 别名的基准，请改为使用绝对别名：

```diff [nuxt.config.ts]
+ import { fileURLToPath } from 'node:url'
+
  export default defineNuxtConfig({
    alias: {
-     images: './assets/images',
+     images: fileURLToPath(new URL('./assets/images', import.meta.url)),
    },
-   typescript: {
-     tsConfig: {
-       compilerOptions: {
-         baseUrl: '..',
-       },
-     },
-   },
  })
```

## Nitro v2 兼容性

上面列出的 Nitro v3 变更涵盖了大量服务器代码。在 Nuxt 5 能够构建之前，你不必完成所有这些工作。Nuxt 5 包含一个兼容层，可以原样运行旧版服务器代码，因此你可以先升级，再进行迁移。

### 模块服务器代码

模块会自动获得兼容支持。如果某个模块的服务器文件从 `h3`、`nitropack`、`#internal/nitro` 或 `#imports` 导入，Nuxt 就会为该模块提供其代码所需的内容：h3 v1 辅助函数、映射到 Nitro v3 的旧版 `nitropack` 路径、`useRuntimeConfig(event)`，以及 v1 事件属性。

构建过程会告知你哪些模块受到了影响：

```text
WARN [NUXT_B9003] Nitro v2 compatibility was applied to server code from 1 module, because of what it imports:
  - some-module (imports `h3`, `nitropack/runtime`)
```

你无需处理此通知。它是提供给模块作者的，也表明该模块的后续版本将不再需要此兼容层。

::read-more{to="/docs/guide/modules/server-compatibility"}
如果该模块由你维护，请了解如何编写可在任一 Nitro 版本上运行的服务器代码。
::

### 你自己的 `server/` 目录

默认情况下，你自己的服务器代码不会获得兼容支持，因为遇到的错误会指出需要修改的地方。如果你希望在完成这些工作之前先发布升级版本，请启用 `nitroLegacy`：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitroLegacy: true,
})
```

启用后，`import { defineEventHandler, getQuery } from 'h3'`、`useRuntimeConfig(event)`、`defineNitroPlugin`、`cachedEventHandler`、`useEvent` 以及未注册 `route` 的处理程序都仍可正常工作。

每个部分都有独立的开关，因此你可以逐个迁移：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitroLegacy: {
    h3: true, // `h3` resolves to the h3 v1 helpers
    specifiers: true, // `nitropack`, `nitropack/runtime`, `#internal/nitro`
    runtimeConfig: true, // the `useRuntimeConfig(event)` signature
    imports: false, // the Nitro v2 auto-import names
    config: false, // Nitro v2 config shapes and removed-option warnings
  },
})
```

`beforeResponse` 和 `afterResponse` 钩子无需开关。只要兼容层处于启用状态，无论是为你的代码还是为某个模块启用，Nuxt 都会从 Nitro v3 的 `response` 钩子发出这些钩子，并报告所有无法处理的情况。

### 兼容层不涵盖的内容

- **未声明的依赖。** `nitropack` v2 会将自身的依赖打包到服务器 bundle 中，因此某个文件可以导入 `lru-cache` 之类的内容，而无需依赖它，也仍然可以正常工作。请将该包添加到你自己的依赖中，或者向需要它的模块报告此问题。
- **类型。** 如果你扩展了 `nitropack/types`，请将其更新到新的模块路径。参见[路由规则类型迁移到 `h3/rules`](#route-rule-types-move-to-h3rules)。
- **事件对象。** 使用默认构建器时，`event` 是 h3 v2 的事件对象。兼容层会恢复 h3 v2 移除的一些内容，例如 `event.context.nitro`、`event.context._nitro.routeRules`，以及在没有 Node 形状 `event.node` 的运行环境中提供该属性。

### 迁移步骤

1. 升级、构建并阅读通知。`NUXT_B9003` 针对的是模块，因此应由模块作者处理，而不是由你处理。你自己的 `server/` 目录中的错误则需要由你处理。
2. 将服务器导入迁移到 [`nuxt/server`](#server-imports-move-to-nuxtserver)，该入口从 Nuxt 4.6 开始提供；未涵盖的内容迁移到 `nitro/h3` 或 `nitro/*`。迁移期间不要启用 `nitroLegacy`。
3. 仅当你需要在迁移完成前发布时才启用 `nitroLegacy`。然后每次将一个开关设为 `false` 并修复相应问题，直到可以移除该选项。
4. 如果 `NUXT_B9003` 仍列出了某个模块，请检查是否有更新版本；如果没有，请提交 issue。
