---
title: '大多为静态的网站'
description: '为内容和营销网站提供接近零的 JavaScript，同时保留交互岛。'
---

默认情况下，Nuxt 会先对页面进行服务端渲染，然后再对整个页面进行 hydration。对于一个 95% 都是静态文本和图片的页面来说，这些 hydration JavaScript 基本上是额外开销：它会延迟交互，并与内容争夺带宽和 CPU，从而可能损害诸如移动端 PageSpeed 分数之类的指标。

Nuxt 提供了避免在不需要的地方付出这部分成本的组件。这个方案将它们结合起来：

1. **预渲染** 你的内容路由，在构建时完成。
2. 使用 `noScripts` 路由规则，**移除**这些路由上的脚本。
3. 对于需要服务端渲染但不需要交互性的组件，使用 **服务器组件**。
4. 在保留脚本的路由上使用 **延迟 hydration**，这样只有在需要时才为交互付费。

## 预渲染并移除脚本

对于完全没有客户端交互的路由，可在 [`routeRules`](/docs/guide/concepts/rendering#hybrid-rendering) 中组合使用 `prerender` 和 `noScripts`：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    '/blog/**': { prerender: true, noScripts: true },
    '/about': { prerender: true, noScripts: true },
  },
})
```

这些路由会在构建时渲染为纯 HTML，渲染后的页面会省略 Nuxt 入口脚本、导入映射、payload 脚本以及 JS 资源提示。CSS 仍然会包含在内。其结果是页面几乎没有 JavaScript 成本。

::read-more{to="/docs/guide/going-further/features#noscripts"}
详细了解 `noScripts` 会省略哪些内容，以及应用级的 `features.noScripts` 选项。
::

::important
`noScripts` 页面不会进行 hydration。页面上的任何内容都不可交互：没有 `@click` 处理器，没有 `<NuxtLink>` 预取（链接仍然会像普通 `<a>` 标签一样正常工作），也不能从该页面进行客户端导航。仅在你确实需要这种行为的路由上使用它。
::

## 导航至和离开无脚本路由

由于 `noScripts` 页面没有客户端路由器，因此每次导航至该页面或从该页面导航离开时，都会进行整页加载。Nuxt 会为你处理这两个方向的导航：

- 从脚本路由**导航至** `noScripts` 路由时（使用 `navigateTo`、`<NuxtLink>` 或 `router.push`），会触发文档加载，因此目标页面由服务器以无脚本方式提供，而不是由客户端路由器渲染。
- 由于这些路由从不会在客户端渲染，因此当覆盖这些路由的路由规则可以在构建时解析时，它们的页面组件会从客户端打包文件中移除。
- 脚本页面和无脚本页面都会输出声明式的[推测规则](https://developer.mozilla.org/en-US/docs/Web/API/Speculation_Rules_API)标签，使支持该功能的浏览器能够在用户点击链接之前预取并预渲染目标页面。这不会在页面本身运行 JavaScript，并且规则的作用域限定为你的页面路由，因此指向 `/logout` 等服务器路由的链接永远不会被推测性地获取。

启用[实验性的视图过渡](/docs/getting-started/transitions#view-transitions-api-experimental)后，这些页面还会启用跨文档视图过渡，因此整页导航会以动画方式呈现，而不是闪烁：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  experimental: {
    viewTransition: true,
  },
})
```

## 用于服务端渲染小部件的岛屿

静态页面的某些部分仍然适合使用背后有实际逻辑的组件：渲染后的 markdown、语法高亮代码、CMS 内容。可使用[服务器组件](/docs/guide/concepts/server-components)实现这些内容。它们会在服务器上渲染，其依赖项永远不会进入客户端打包文件：

```bash [目录结构]
-| app/
---| components/
-----| HighlightedMarkdown.server.vue
```

```vue [app/pages/blog/[slug\\].vue]
<template>
  <article>
    <h1>{{ post.title }}</h1>
    <HighlightedMarkdown :markdown="post.body" />
  </article>
</template>
```

像这样的静态岛屿在 `noScripts` 路由上也能正常工作，因为它们的 HTML 会在渲染时嵌入。

::warning
岛屿中的完全交互式小部件（标记了 [`nuxt-client`](/docs/guide/concepts/server-components#selective-hydration-with-nuxt-client) 的组件，或交互式岛屿插槽）在 `noScripts` 路由上**无法**工作。岛屿的 teleport 会在 hydration 之前由一小段内联脚本移至正确位置；禁用脚本后，这段代码无法运行，也不会进行 hydration。如果页面需要哪怕一个交互式小部件，也应在该路由上保留脚本，并改用延迟 hydration。
::

## 其余部分的延迟 Hydration

对于需要一些交互功能的路由，应保留脚本，但使用[延迟 hydration](/docs/directory-structure/app/components#delayed-or-lazy-hydration) 控制组件的 hydration *时机*：

```vue [app/pages/index.vue]
<template>
  <div>
    <HeroSection />
    <!-- 永远不需要变为可交互的静态内容 -->
    <LazyTestimonials hydrate-never />
    <!-- 仅在滚动到视图中时进行 hydration -->
    <LazyNewsletterSignup hydrate-on-visible />
    <!-- 在浏览器空闲时进行 hydration -->
    <LazyCookieBanner hydrate-on-idle />
  </div>
</template>
```

`hydrate-never` 在内容型网站上特别有用：组件的 HTML 会在服务端渲染，但它永远不会被 hydration，因此它的 JavaScript 也永远不会执行（不过属性变化仍然会触发 hydration）。

## 整合起来

一个典型的以静态内容为主的网站最终会是这样的：

```ts twoslash [nuxt.config.ts]
export default defineNuxtConfig({
  routeRules: {
    // 纯内容：预渲染，零 JS
    '/': { prerender: true, noScripts: true },
    '/blog/**': { prerender: true, noScripts: true },
    // 带有交互式组件的页面：预渲染，但保留脚本
    '/contact': { prerender: true },
  },
})
```

- 内容路由提供纯 HTML 和 CSS，导航到这些路由时会进行推测性预取的文档加载
- 岛屿（`.server.vue` 组件）负责处理各处的服务端渲染小部件，避免将大型依赖打包到客户端
- 少数交互式路由会保留脚本，并通过 `hydrate-on-visible` / `hydrate-on-idle` / `hydrate-never` 限制浏览器在初始阶段需要执行的工作量
